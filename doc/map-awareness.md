# 地图感知可行性与实现路线

参考资料：[rocom-capture docs](https://github.com/whoisnian/rocom-capture/tree/master/docs)（协议、地图、数据和架构说明）。

## 当前项目到底实现了什么

当前代码的真实链路是：查找窗口标题 `洛克王国：世界` -> Windows `PrintWindow` 或屏幕区域截图 -> YOLO 找标题/精灵槽位 -> OCR 和 DINO/ONNX 特征匹配。`MapAwarenessTrial.tsx` 目前仍使用随机移动、静态 POI 和静态精灵数组，地图画布是演示数据，不是实时游戏数据。

新增的 `GET /map_observation?trial=grass` 只返回一次真实截图观测：窗口是否存在、截图尺寸、标题 OCR、地图名和识别耗时。`position`、`heading`、`wild_pets` 明确保持 `null`/空数组，直到有协议解析器或训练好的视觉模型提供证据。

> 注（2026-09-01 订正）：本节描述的是早期状态。此后 `/map_observation` 已移除了全部徽章试炼相关逻辑（`trial` 参数、标题 OCR、地图名），只做「窗口截图 + 小地图玩家定位」，详见 `minimap-localization-manual.md` 10.2 节。徽章试炼的关卡识别（图1-3 标题 OCR/分类）属于跟随识别链路，与本文的开放世界地图感知是两个独立功能。

## 对照 rocom-capture docs 的抓包结论

参考项目文档描述的是游戏客户端到服务器的 TCP 8195 连接和 tsf4g/GCP 协议：

1. TCP 必须先重组为连续字节流，再按 `0x3366` magic、`hdr_len`、`body_len` 切 GCP 包。
2. `0x1002 ACK` 的 header 扩展区明文包含本次连接的 16 字节 AES-128 会话密钥；不能从连接中途开始抓而没有密钥。
3. `0x4013 DATA` 使用 AES-CBC，解密后还要剥离 internal header，再按 protobuf 解析应用消息。
4. 位置需要跟踪 `0x0152` 进入场景、`0x015c` 传送、`0x0133` 移动；洞穴/楼层需要 `0x0414` 区域进出事件。位置是 UE 厘米坐标，朝向是 `FRotator*10` 的 yaw，不是普通二维像素坐标。
5. 野生精灵、POI、地图底图和分层图还依赖游戏数据表/资源索引，单纯解析一个移动包不能得到完整地图。

## Windows 可行性

**技术上可行，工程上属于高风险逆向功能。** Windows 本身能完成：

- 抓包：Npcap + Wireshark extcap、WinDivert，或基于 ETW/WFP 的受控采集；通常需要管理员权限。
- TCP 重组/AES/protobuf：Python/C++/Rust 均可实现，建议抓包层与 Flask/前端解耦。
- 截图：本项目已有 `PrintWindow`/`ImageGrab`，但硬件加速、独占全屏、窗口最小化、DPI 缩放和反作弊都会导致黑帧或坐标偏移。

主要风险是协议和资源版本变化、TLS/额外封装、密钥只在连接建立阶段出现、管理员权限安装 Npcap、以及对第三方服务进行未授权抓包可能违反服务条款。发布功能前应先确认授权和用户知情；不要把密钥、原始 pcap 或账号数据上传服务器。

建议的抓包 MVP：Npcap 过滤目标进程/目标 TCP 连接；保存环形缓冲而非全量 pcap；验证 GCP framing；只实现 ACK 取 key、DATA 解密、`0x0152/0x015c/0x0133/0x0414` 四类消息；用离线脱敏样本做回放测试；最后通过 localhost WebSocket 推送统一事件：

```json
{
  "scene_res": 10003,
  "position_cm": {"x": 123, "y": 456, "z": 0},
  "yaw_deg": 90.0,
  "areas": [],
  "source": "packet",
  "confidence": "protocol"
}
```

不要在没有密钥、场景资源或字段验证时回退成随机坐标；应返回 `unknown` 并在 UI 标出来源。

## 如果不能抓包：推荐的视觉路线

视觉方案可以在 Windows 上落地，但能力边界不同：

### 第一阶段：可靠的窗口采集

保留 `hwnd` 模式，失败时降级 `grab`；记录 DPI、客户区矩形和截图时间戳。建议使用 DXGI Desktop Duplication/Windows Graphics Capture 作为后续高帧率采集器，避免 `PrintWindow` 对 GPU 游戏返回黑帧。

### 第二阶段：地图/角色/朝向检测

- 地图名：保留现有标题 YOLO + OCR；输出字符置信度和地图分类相似度，低于阈值时显示未知。
- 玩家位置：训练 YOLO/RT-DETR 检测玩家角色或固定 UI 罗盘，再做模板匹配/关键点定位。只有存在稳定小地图或固定坐标 UI 时，才能得到像素坐标；将像素坐标映射到世界坐标需要每张地图的标定点和仿射/单应矩阵。
- 朝向：优先识别角色朝向箭头/罗盘指针；没有明确指针时不要从单帧角色姿态猜 yaw，使用连续帧光流/跟踪并输出较低置信度。
- 野生精灵：训练“精灵实体/名称牌/交互气泡”检测器，再对检测框做图标特征匹配和 OCR。遮挡、动画、同屏重叠时要做多帧跟踪（ByteTrack/OC-SORT），不要把单帧框直接当作刷新事件。

### 第三阶段：时序融合

以 5–10 FPS 采集；每个观测带 `timestamp`, `bbox`, `track_id`, `confidence`, `source`。用卡尔曼滤波或简单匀速模型平滑位置，连续 N 帧确认进入/离开；地图切换用 OCR/视觉分类的迟滞阈值，避免标题动画造成抖动。前端地图应显示“视觉估计”而不是“协议坐标”。

### 数据和验收

至少采集每张地图、不同分辨率/DPI、窗口遮挡/最小化、昼夜/特效、角色移动和传送的带时间戳截图；按地图/场景划分训练集和验证集，避免同一段视频泄漏。验收指标建议为：世界地图定位准确率、玩家中心像素误差、yaw 平均绝对误差、精灵检测 mAP、连续跟踪 ID 切换率，以及 10 分钟运行的 CPU/GPU 占用。

## 推荐决策

先把当前页面从模拟数据源改成“真实截图观测 + 明确未知状态”，验证 Windows 采集稳定性；并行做一个离线 GCP 解码器，只对已授权样本验证协议。若抓包链路能稳定拿到 ACK、DATA 和四类场景事件，再接入实时地图；否则把视觉方案限定为地图名、屏幕位置和可见实体，不承诺服务器级坐标、楼层和刷新列表。
